# ADR — Normal Data run-to-specialist promotion boundary

**Status:** Proposed (implementation gates; not an authorization grant)  
**Date:** 2026-10-10  
**Applies to:** Slice D of [ADR_NORMAL_DATA_MODE.md](ADR_NORMAL_DATA_MODE.md)

## Decision and existing invariants

The Normal Data comparison domain (schema v25–v27) is **working data**, not controlled audit evidence. Its completed run stores a recipe-version UUID, both SHA-256 digests for source *bytes read at execution*, a result digest, and immutable result JSON. It does **not** retain both source files or establish an authenticated approver. Historical run viewing must remain possible after a linked source moves, changes or disappears; historical viewing must not assert that source bytes remain available.

The accepted [ADR-0007](ADR-0007-evidence-capture-and-signoff-binding.md) requires formal review to bind exact workpaper revisions and captured controlled-evidence versions. A Normal Data run cannot satisfy that requirement by a link to a filename, current document, "latest" dataset, result digest alone, or a Tauri caller's asserted actor name.

## Trust/authorization constraints

1. Keep **working-data reference**, **promotion request**, **controlled capture**, **specialist attachment** and **review/sign-off** distinct states; labels and progress metadata must not imply authorization.
2. Every requested promotion must be an explicit user action identifying a **specific completed comparison-run UUID**, exact **recipe version**, source dataset versions and hashes, and an exact target **workpaper revision** or specialist target supported by the relevant domain. No implicit promotion on save, run, search, view or export.
3. Validate the stored immutable run against the frozen recipe, dataset A/B identities, immutable source hashes and persisted result digest. Do not reinterpret a changed linked source as historical input. Source hashes and result digest have different meanings.
4. Before declaring preserved source evidence, resolve approved-root source identities through the existing native canonical path boundary; read stably and verify exact size and SHA-256 against the *historical run* for both sources; capture each original via the existing controlled-evidence workflow into retained immutable storage. If either is missing, changed, unreadable or capture fails, **do not finalize**.
5. Preserve the stored run result as its own immutable, versioned artifact if reviewers must rely on that computation (a stored JSON record alone does not prove retained original source bytes). Any representation must bind the exact frozen run and result digest, not a new computation on latest inputs. Do not silently treat cached previews or computed output as captured originals.
6. Do not append a new evidence link to an existing signed/reviewed workpaper revision and imply that the prior sign-off covers it. Material new attachments require a new revision and subsequent review under existing specialist lifecycle rules. Do not modify historical sign-offs.
7. **No authenticated role authorization is currently established by the Normal Data feature.** Never infer it from `actor_id`, role strings, client association, button visibility or an asserted Tauri argument. A formal cross-domain promotion command must fail closed until its caller identity, permission to read the source workspace, permission to modify the exact specialist target, and review-state policy are actually enforced and tested.
8. Do not expose arbitrary file paths, source bytes, or uncontrolled document identifiers to the frontend. No new filesystem grants, external upload service, or auto-promotion facility is warranted.

## Safe implementation sequence

**D1 — native inspection only.** Add a bounded, read-only provenance/readiness query that takes only a completed run UUID. Resolve frozen recipe/dataset identities from the database, return source A/B SHA-256 and result SHA-256 together with their distinct meanings, and indicate integrity preconditions. The query must not capture, attach, mutate, or claim authorisation. A historical receipt is available even when linked source bytes have changed; any live verification status is a new, separately labelled observation.

**D2A — live source-integrity preflight (implemented separately from authorization).** An explicitly invoked native command re-resolves exact dataset versions and re-reads both linked sources through the approved-root, stable-read, bounded SHA-256 verifier. Return two timestamped observations only if each matches the historical run's exact source hash. Reject changed, unavailable and invalid sources without any capture, attachment, state mutation or authorization grant. These reads are sequential and do not produce an atomic two-file snapshot or a durable preservation guarantee.

**D2B1 — internal authorization/target-state policy (implemented as fail-closed infrastructure; NOT a usable permission system).** An internal Rust-only policy requires a caller identity type that **cannot be constructed in the production build** until a trusted authentication adapter is implemented. It requires separate explicit permissions to read the exact Normal Data workspace, attach evidence to the exact engagement, and modify the exact workpaper revision. It validates source-run workspace membership and the workpaper/engagement/revision foreign-key chain; only current unsigned DRAFT, NOT_STARTED or IN_PROGRESS revisions of active workpapers/engagements/clients are eligible. Reject reviewed/final stages, any sign-off on the revision, unresolved review notes, a superseded revision, missing or mismatched resource scope. It is **not registered as a Tauri command**, performs no write and returns no reusable authorization token. A test-only constructor and test-only grants validate the policy matrix; they do not ship as runtime auth.

**D2B2A — durable, revocable, narrowly scoped grant evaluation (implemented, backend-only; still not authenticated promotion).** Schema v28 introduces a default-empty subject enrollment and exact-resource grant registry with only three permitted scopes (Normal Data workspace read, engagement evidence attachment, specific workpaper revision write). SQLite CHECK constraints and immutability triggers forbid changing grant owner, resource, permission, grant expiry or reactivating a revoked grant; subjects can only be disabled, never silently re-enabled. The read-only native `SqlitePromotionPermissions` provider checks an already-verified principal UUID, registered active subject, exact permission and resource UUID, nonexpired and nonrevoked grant, and immediately denies missing/invalid/error cases. A future authority must perform provisioning and attestation; no user-facing grant, enrollment, or identity command is installed and the production principal constructor is still absent. These local SQLite records must **not** be mistaken for authenticated identity or cryptographically protected grants against a local database administrator.

**D2B2B1 — native-only transactional grant administration skeleton (implemented; authority not connected).** Schema v29 adds an immutable, append-only administrator-action ledger for subject enrollment, exact scoped grant issuance, one-way revocation and subject disabling. The internal `normal_data_permission_admin` service requires a `VerifiedGrantAdministrator` whose constructor is **test-only**; there is no production issuer, session, admin privilege or frontend/Tauri binding. Resource membership/active target, subject enrollment, expiry and exact scope are checked before issue. Each grant mutation and audit receipt must commit in the same immediate SQLite transaction or neither persists. Negative tests verify audit-failure rollback, duplicate/expired/missing grants, irreversible revocation/disable and zero evidence links. Existing v28 rows remain readable; migration v29 creates no accounts or grants. Audit rows and policy configurations are local database integrity controls, not tamper-proof authority against a compromised database owner.

**D2B2B2A — transaction-bound policy gate (implemented internally; not a promotion feature).** The native-only `with_authorized_transaction` helper requires `VerifiedPrincipal` (still test-only constructible), obtains a SQLite `IMMEDIATE` transaction, checks three exact nonexpired/nonrevoked grants, re-inspects frozen Normal Data result/source hashes on the **same connection**, checks current engagement/workpaper/revision/review/sign-off state on the same transaction, and executes a native callback followed by commit only when all pass. If policy or callback fails, no callback or transaction changes may persist. Another SQLite writer cannot interleave revocation/review-state updates between authorization and commit; tests demonstrate lock contention, rollback, and that a later revoked grant or reviewed revision fails closed. This is a **database concurrency property only**: it does not lock external CSV sources, retain artifacts, prove authenticated identity, or grant permission from a prior preflight. No Tauri command exposes it.

**D2B2B2B1 — exact transient three-artifact material (implemented, internal-only; NOT retention).** The private native `normal_data_preservation_material` adapter constructs a bounded, in-memory `PreservationMaterial` from an exact completed comparison-run UUID: original A and B bytes from the approved-root stable-read SHA-256 verifier (at most 32 MiB per source), and the exact stored result JSON bytes (at most 8 MiB). It requires the frozen historical provenance/recipe/source-version chain and re-verifies the immutable result's **semantic** comparison digest. It also computes a **separate SHA-256 of the exact serialized result artifact**, distinct from the semantic result digest and from both original source hashes. A same-length edited source, missing source, or altered result prevents material creation. The API is not a Tauri command and creates no evidence records, links, files, approval token or audit event; its raw bytes remain internal. Reading A and B sequentially does not preserve their state outside the returned byte buffers or establish an atomic two-file file-system snapshot.

**D2B2B2B2A — private verified on-disk staging and recovery inventory (implemented internally; NOT controlled evidence).** Native-only `normal_data_staging` accepts only the three bounded, verified byte buffers produced by the prior material adapter. On an explicitly supplied **trusted, existing private staging root**, it writes three exact artifacts and an identity/digest-only versioned manifest into a unique UUID-named `.partial` directory using create-new files and file sync; rereads and checks all three bytes, then renames the package to `.ready` and syncs its containing directory where the OS supports it. Scan/reopen **rechecks** every source byte SHA-256 and both result-byte and semantic digests, marks corrupt packages unavailable, detects interrupted `.partial` packages, and permits internal cleanup *only* of incomplete packages. Tests verify exact staged content, scan across reopen, same-size tampering, bad source/result bytes, incomplete recovery and symlink/insecure-root denial on Unix. Staging never creates SQLite evidence versions, links, approvals or signoffs and has no frontend/Tauri command. This is **crash-inspectable working-data staging**, not power-loss-safe or tamper-proof retention: Windows lacks portable directory fsync, and the storage root must be protected from hostile local writers. The current interface intentionally cannot convert a staged package into reviewed evidence.

**D2B2B2B2B1 — exact staged-run and current-target reconciliation (implemented, native-only; NOT approval).** An internal `normal_data_staged_policy::inspect_authorized_staged_run` requires the unavailable-in-production `VerifiedPrincipal` and enters the existing SQLite `IMMEDIATE` transaction gate. It rechecks all three scoped grants, live subject and target eligibility, immutable completed-run provenance, and then reads a private ready stage *inside that same transaction*. The staging verifier checks each staged source's dataset/document/content-version IDs and original SHA-256 against trusted SQLite values; it also checks stage run/workspace/recipe identities and **exact JSON-byte SHA-256 freshly derived from the frozen run's database `result_json`**, in addition to its independent canonical semantic digest. A hash-consistent but swapped run, altered source identity, or whitespace-altered result (with recomputed stage-local byte hash) fails the bound check. Revoked permissions and reviewed targets deny immediately. It only returns a metadata observation and does not issue reusable authorization, capture evidence or mutate workpapers. Directory/filesystem mutation outside the SQLite lock remains possible; a future final retention/linkage write must verify again. Tests explicitly validate the distinction between standalone stage integrity and cross-domain, transaction-scoped identity/permission binding.

**D2B2B2B2B2A — append-only private staging recovery observation journal (implemented, NOT controlled evidence).** Schema v30 introduces default-empty `normal_data_stage_recovery_scans` and `normal_data_stage_recovery_entries`, with SQLite constraints, foreign keys, and update/delete prevention triggers. The internal `normal_data_stage_recovery_journal` service performs a bounded, native-root filesystem inventory and then records an immutable scan header and all observed package states in one `IMMEDIATE` SQLite transaction: `READY_LOCAL_HASH_VALID`, `READY_CORRUPT`, or `PARTIAL_INTERRUPTED`. Failure rolls back all rows. On later scans, old records remain unchanged while new observations capture changes such as same-size corrupted staged bytes; read-back checks scan entry counts. Records deliberately contain only scan/stage UUIDs, timestamps, counts and local status, no file paths, original bytes, evidence IDs, or asserted principal. **Scan and SQLite commit are not one filesystem snapshot:** a status may already be stale when recorded. `READY_LOCAL_HASH_VALID` means only that a package matched its own manifest during this scan; it does not attest immutable-run identity, authorization, source availability, controlled retention, or tamper resistance against a local storage/DB owner. No Tauri API or production authentication is installed. Schema migration v29→v30 adds no grants/evidence; it remains default-empty.

**D2B2B2B2B2B — trusted identity, durable capture lifecycle and authorized specialist linkage (not implemented).** Establish real native authentication/session identity, administrator privilege mapping, secure local-data threat model and audited grant issuance. Define enforceable private storage ownership, crash/power-loss fsync/recovery, retained immutable controlled-evidence versions for **both originals and the exact result artifact**, idempotency, quarantine and cleanup across database/filesystem failure, and append-only capture/retention audit events. Verify the three retained bytes/hashes, and recheck grants, engagement/revision eligibility and provenance inside a final SQLite write transaction before linking exact controlled versions. Staged `.ready` bytes are NOT eligible for formal review or specialist promotion today.

**D3 — controlled, atomic linkage.** After D2, use an explicit request to capture (or refer to rigorously verified retained copies of) each required original and the result artifact, then transactionally bind the exact versions to a newly reviewable specialist revision with append-only audit history. Refuse wrong versions, mismatched hashes, concurrent target changes, archived targets, missing permission, incomplete capture and signed-revision mutation.

**D4 — UI.** A human-confirmed promotion flow may be added only after D2/D3, displaying the selected immutable run/source IDs, target revision, capture policy, permissions and verification status. Avoid a misleading "Promoted" badge for a working-data reference.

## Minimum negative regression matrix

- No client, engagement or workpaper requirement for ordinary workspace creation, dataset declaration or comparison execution
- Unknown/malformed run UUID and forged source/recipe/version identifiers are rejected
- Same-size changed linked bytes and moved/unavailable source cannot be considered verified historical sources
- Fingerprinted-only source cannot become controlled evidence via an asserted hash
- A stored result digest cannot be substituted for either source digest
- Historical run remains inspectable after linked-source changes, without a false current-verification claim
- No attached evidence or signed-off workpaper may be mutated indirectly by a read-only operation
- Wrong workspace, wrong engagement, unauthorized caller, finalized/signed revision, and capture failure block future promotion
- Existing ledger/TB/FS specialists and controlled evidence capture stay unchanged

## Scope of D1

D1 supplies provenance and policy clarity, **not promotion**. A valid UUID and database record are not proof of permission to attach it to any specialist target. Subsequent code reviews must verify current code and migration behavior against this ADR, not infer these capabilities from wording.
