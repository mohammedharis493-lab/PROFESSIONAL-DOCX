## Production call-chain facts

`capture_controlled_evidence` is a **registered callable Tauri command**, accepts a webview-provided UUID for a file instance, and passes it into the native `evidence::capture_controlled_evidence` pipeline, without an independently verified engagement-scoped principal or capture grant in the inspected handler.

The normal native file-capture pipeline calls `persistence::begin_evidence_capture`, which uses an `IMMEDIATE` transaction, checks the indexed file/document is live and the root/file available, creates the `CAPTURING` job and `EVIDENCE_CAPTURE_STARTED` audit with NULL actor. The file pipeline then validates the indexed source, copies bytes into an exclusive temporary controlled file, hashes bytes during copy, compares source file identities/sizes/timestamps before and after copy, renames to final location, independently rehashes the final file and sets it read-only. Only **after those steps** does it invoke `persistence::complete_evidence_capture` with the captured digest, file identity, locator and size. The outer pipeline tries to record a `FAILED` transition if capture fails; it does not promise cleanup of every filesystem side-effect in all crash/error cases.

The *separate lower-level persistence completion* is an `IMMEDIATE` SQLite transaction that demands a still-`CAPTURING` job with matching document/file-instance IDs, allocates a per-document version number, records a `HASH_VERIFIED` source-content version, controlled-evidence metadata, the document `CONTROLLED_EVIDENCE` storage state, a `COMPLETE` job transition and `EVIDENCE_CAPTURE_COMPLETED` audit with NULL actor. SQLite rolls back these DB writes if a later insert fails. This helper **does not independently re-read managed bytes, recompute the supplied hash or locator, recheck parent `documents.archived_at_ms IS NULL` or authenticate a publisher**; it relies on the ordinary caller pipeline. It is not itself a registered Tauri command and cannot be invoked directly from the installed webview using the existing exposed command set.

`persistence::finish_evidence_capture_failure` supports only `FAILED`/`QUARANTINED`, takes `IMMEDIATE`, changes `CAPTURING` to a terminal state, emits a NULL-actor failure/quarantine audit and is a no-op for missing/already-terminal jobs. The normal capture caller maps its actual errors to `FAILED`; a test-only direct call to `QUARANTINED` does not establish an installed caller reaching that state. The terminal state prevents the same job completing.

**Read versus attach:** `evidence::read_controlled_evidence_bytes` separately validates archive, exact locator, root containment, size and recomputed digest. Statutory assessment attachment instead accepts existing retained/hash-verified **metadata** without rereading controlled bytes and without an archive or client/engagement association check; see [statutory assessment dependency](WORKPAPER_STATUTORY_ASSESSMENT_AUTHORITY_DEPENDENCY_DRAFT.md). Do not conflate these three different trust stages.

## Additional real-migration test-only characterization

[`src-tauri/src/workpaper_controlled_capture_native_tests.rs`](../../src-tauri/src/workpaper_controlled_capture_native_tests.rs) uses production migrations and **directly fabricates a syntactically valid SQLite capture-job/file/document/root lineage in disposable fixtures**. Its four cases call lower-level *persistence methods*, not registered installed Tauri IPC:

1. Wrong document/file-instance identity is refused with unchanged source versions, controlled versions, audit and job counts; original capture stays `CAPTURING`.
2. A `FAILED` transition records exactly one NULL-actor failure audit and rejects future completion; repeated terminal transition is an unchanged no-op. A separate directly synthesized `QUARANTINED` transition is characterized without asserting installed quarantine reachability.
3. When a **fixture already has a CAPTURING job but its document is then archived**, the lower-level completion still records caller-provided 32-byte SHA-256, noncanonical synthetic locator and `HASH_VERIFIED` metadata, despite **no file bytes anywhere in the synthetic fixture**. The normal read-record path hides the archived document. This demonstrates persistence's *delegated trust* and archive-recheck limitation, NOT that installed capture skips verification; the ordinary `evidence::perform_capture` hashes real bytes first.
4. A duplicate `controlled_evidence_version_id` on a second synthetic job rejects under the migrated schema, with no partial extra source-content/version/audit writes, unchanged original version and second job still `CAPTURING`.

[Node source-only tripwires](../../tests/workpaper-firm-library-boundary.test.mjs) check the production normal-copy hash/stability steps remain distinct from the lower-level completion, its `IMMEDIATE`/identity/terminal/audit boundaries, the test-only module registration and 9/34 direct denial ledger.

No file-capture task or professional approval is signed by these fixtures. No shipping Rust, registered handlers, UI Save, SQLite migration or evidence bytes were altered.

## Real-byte post-rename / pre-database-commit fault-injection (additional test-only characterization, 2026-10-21)

**Different fixture class from the synthetic metadata tests above:** the two new `#[cfg(test)]` cases in [`src-tauri/src/evidence.rs`](../../src-tauri/src/evidence.rs) use existing native `TestEvidence` to **create real source files, run the native indexer, copy real bytes, rename the controlled file, rehash actual preserved bytes and mark it read-only**. They call the native `capture_controlled_evidence` function directly, NOT the registered Tauri IPC or an authenticated actor. The only fault injection is an SQLite trigger installed in the disposable **test database**, never a production migration.

- **Controlled-evidence version INSERT rejection after final-file rename.** A synthetic `BEFORE INSERT ON controlled_evidence_versions` RAISE abort forces `complete_evidence_capture` to rollback. The outer capture path records the job `FAILED` and one NULL-actor failure audit; there is no new controlled-version row or source-content-version row. **The already-created, read-only controlled file with its actual copied bytes remains on disk, outside the metadata lookup.** After dropping the injected trigger, a fresh capture succeeds, is readable through the real byte-integrity reader and receives a different UUID. The first unindexed file still remains after the successful retry; no automatic orphan reconciliation is observed.
- **Completed-audit INSERT rejection at the final DB-transaction step.** A synthetic trigger refusing only `EVIDENCE_CAPTURE_COMPLETED` causes the entire completion transaction to roll back, including already-inserted source content, controlled version, document storage-state update and completion status. The outer error handler still creates `FAILED` audit and job state. Yet the read-only final controlled file of verified real copied bytes remains on disk with no metadata version and is not addressable by normal `get_controlled_evidence_read_record`.

These are **demonstrated cross-resource atomicity gaps on the native function path under deliberately injected DB errors**, not evidence tampering, a grant failure, a Tauri exploit, a claim that every error leaves an orphan, or proof of crash recoverability. In particular, SQLite rollback is working: the discontinuity is between **filesystem preservation** and **SQLite commit**, which are not a single atomic transaction. The tests restore permissions and remove disposable test files at teardown; they neither delete nor repair existing user custody records.

Any remediation must preserve legally retained evidence; do not apply automatic deletion before independent review. Separate DEC-02/03/04/06 authority and installed handler tests remain unresolved. Two source-only Node tripwires pin the rename → rehash → readonly → SQLite completion ordering and presence of test-only regressions; these are not proof of production permission enforcement.
