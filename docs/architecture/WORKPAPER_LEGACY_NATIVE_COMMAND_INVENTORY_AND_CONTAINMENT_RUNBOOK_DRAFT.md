## 1. Trust boundary and inventory interpretation

The source-level call graph is `src/App.tsx` form → `invoke("command", payload)` → registered `#[tauri::command]` handler in `src-tauri/src/lib.rs` → `src-tauri/src/persistence.rs` → SQLite. The registration is in `tauri::generate_handler!` (lib.rs **lines 5326–5355 approximately; locate by command name if line numbers drift**); the three workpaper commands **are installed/callable**, irrespective of whether a visible frontend form is disabled. Read this as application/local-webview command availability, **not demonstrated Internet reachability or external exploitability**. Risk severity depends on DEC-02 device/webview/OS-account threat assumptions.

The current detached seven-field revision helper, test-only native successor and fixture sessions are NOT registered Save/signing commands. The presence of `#[cfg(test)]` checks, green CI, or a warning on a form cannot authenticate a user or restrict the underlying legacy handlers.

**Adjacent interpretation:** the reviewed/cleared state is a database workflow fact, **not** evidence of an independently authenticated practitioner. This matters because `create_workpaper_signoff` currently checks unresolved review notes for reviewer/final labels, so a user-asserted `clear_review_note` event can affect that prerequisite. Cross-checks on linked evidence or note-state transition do not replace native per-person, per-workpaper reviewer authorization or segregation of duties (DEC-03/04/06/08). This is a source-level risk inference and test characterization, **not** a demonstrated external attack or authorization to disable legacy workflows.

### Non-authorizing actual-SQLite fixture coverage added to PR #137

Four `#[cfg(test)]` native persistence tests, using a disposable database initialized from production migrations, characterize: caller-selected actor label recorded in a `REVIEWED` workflow transition; caller-selected raiser, owner, responder, clearer and reopener labels preserved in real review-note records/events; wrong-workpaper review-note revision rejection **without any new workflow/note/event/audit row**; and empty response or premature reopening rejected with identical write counts and unchanged OPEN note. **These test current legacy persistence behavior, not real `tauri::invoke` reachability, a trusted native issuer, reviewer authentication or a completed privilege-denial test.** Tests must be revisited/rewritten if an authorized gate later changes the expected behavior.

### Direct-native command acceptance tests to implement ONLY after an approved L2/L3/L4 scope

- Reject a caller who supplies `actorId`/`raisedBy`/`ownerId` claiming a different reviewer; no state, note, event, audit, evidence or sign-off mutation. Do not use fixture-constructed person labels as positive auth.
- Reject missing/expired/revoked grants, workpaper/engagement mismatch, archived workpaper, reviewer/clearer privilege mismatch and conflicts in current revision/evidence; demonstrate denial through the **registered Tauri handler**, not only direct `persistence` functions.
- Preserve correct native state-machine denials (invalid reopen, cleared-response, duplicate clear), and verify audited authenticated actor identity from a trusted session independent of payload fields.
- Demonstrate two distinct legitimate principals with scoped permissions can use intended workflows; test against real current revision/evidence and exact note ownership with concurrent writers.
- Preserve readable old workflow/note/audit histories and clear provenance caveats on exports; test offline and old installations, backup/restore, rollback and supported platform differences before deployment.
- Fail closed when the trusted issuer is unreachable or undecided. **Until approval, no production issuer, gate or grants should be silently introduced.**

### Test-only writer-lock denial smoke reference — NOT direct Tauri proof

`src-tauri/src/workpaper_legacy_command_denial_candidate.rs` is a **new `#[cfg(test)]`-only module**, registered only for Rust unit tests, absent from shipping binaries and unregistered in `tauri::generate_handler!`. It enumerates the eight legacy work-intent *categories*, enters an isolated actual-migration SQLite database using `TransactionBehavior::Immediate`, and invokes only a `DenyAllLegacyWriter` check **before** an unreachable synthetic audit write probe. Three Rust tests exercise all eight categories, multiple claimed actor/role strings and target IDs, comparing the workpaper/revision/evidence/sign-off/supersession/workflow/review-note/event/audit counts before and after denial. The allowed-branch probe is **not production logic**, and there is deliberately **no fixture-positive or shipping authority** in this module. Two Node source checks guard its test-only registration and fail-closed untrusted-actor signature.

**Coverage distinction:** these checks show that the **nonshipping prototype** refuses to write under a real SQLite writer lock; they do **not** dispatch or intercept any of the eight existing registered Tauri handlers, deny any real user, prove real session identity, or execute any of the 30 planned direct-handler cases. The JSON matrix must continue to report `liveTauriCommandDenialHarness: NOT_IMPLEMENTED`, `execution: NOT_IMPLEMENTED` and `result: NOT_RUN` on **all 30**. Neither the module nor these tests selects an L1–L4 containment option or resolves DEC-01–08. Only human-approved implementation and independent native boundary review could do that.

## 3. What is contained today versus still callable

**Already present in this draft/source baseline:** legacy three-field UI displays an explicit draft/unverified warning; its submit refuses creating a successor when it has observed an existing revision, does a fresh list, and sends `initialOnly: true`; the actual native `IMMEDIATE` transaction rejects a second initial revision when that flag is true. The sign-off UI discloses caller-entered actor details. Detached revision UI and the `#[cfg(test)]` successor are isolated. Real SQLite migration tests characterize stale full-snapshot append, sign-off spoofed identity labels, no-op revision append/supersession, immutable history and missing evidence carry-forward. **These are partial containment and characterization, not native-grant access control.**

**Still callable:** `create_workpaper_revision` with missing/false `initialOnly`; `create_workpaper_evidence_link`; `create_workpaper_signoff`; and adjacent registered workpaper-state/review commands. A frontend warning, disabled button or detached editor does NOT remove any of those IPC/native entry points. There is no shipping `expectedLatestRevisionId` CAS editor route, independently bound signer, reviewed `READ_WORKPAPER` / `REVISE_WORKPAPER` grants, or authenticated approval path.

## 5. Reversible rollout / historical-data preservation plan (PROPOSAL ONLY)

**Phase 0 — nonmutating reconnaissance:** identify supported build versions and OS/filesystem scope; produce a reviewed inventory of installed caller versions, local/offline usage, integrations and any consumers of sign-off/provenance exports. On **approved copies** of databases only, capture a transactionally consistent backup, schema/migration version, a privacy-minimizing count of workpapers, revision chains, sign-offs by claimed type, active/superseded state, exact evidence links, controlled versions and relevant audit events. Do not extract actor identities or confidential content into a GitHub issue. Record encryption/storage/retention expectations under DEC-05/07.

**Phase 1 — compatibility rehearsal, no shipped change:** for each L1/L2/L3 candidate, rehearse on isolated fixture/copied data: (a) opening and exporting old seven-field revisions with nonempty Unicode/whitespace in the four fields omitted by the old UI, (b) reading superseded sign-offs and exact version IDs, (c) reproducing old calls omitting `initialOnly`, (d) attempted write via direct native IPC rather than React button, (e) current-version UI on an existing workpaper, (f) offline startup and unavailable issuer, (g) protected backup/restore + rollback of application **without rolling back or rewriting legitimate immutable user records**. Stop if unsupported cross-version schema downgrade would destroy rows.

**Phase 2 — owner decision gate:** named product and security humans select L1/L2/L3 or independently reviewed L4, state which exact commands are affected and what to do with old caller-asserted approval labels. Record before/after usability, read-only availability, deployment channels, default flags, reversal, on-disk compatibility, source code owner and accountable sign-off. Resolve DEC-02/03/04/05/06/07/08 as applicable; unresolved items do not default to accept.

**Phase 3 — separately approved implementation/release:** only after the gate, implement native-level denial or verified authorization in a different reviewed change, with direct Tauri command tests, no bypass from old payload shapes, archived-workpaper checks, denial no-mutation, expected-base/evidence-only race checks, exact version/Unicode losslessness, restore, and negative signer identity/grant/revocation. Stage rollout; monitor errors without disclosing confidential workpaper contents. Retain old immutable records and never retroactively label them verified.

**Rollback rule:** rollback of code/gate must not rewrite historical signed rows, recreate forged sign-offs, silently re-enable an unsafe API, or depend on destructive SQLite downgrades. If backward compatibility is impossible, remain read-only with an explicit human-reviewed migration and restore path.
