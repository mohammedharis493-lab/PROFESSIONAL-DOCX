## 1. Trust boundary and inventory interpretation

The registration is in `tauri::generate_handler!` (lib.rs **lines 5326–5355 approximately; locate by command name if line numbers drift**); the three workpaper commands **are installed/callable**, irrespective of whether a visible frontend form is disabled. Read this as application/local-webview command availability, **not demonstrated Internet reachability or external exploitability**. Risk severity depends on DEC-02 device/webview/OS-account threat assumptions.

The current detached seven-field revision helper, test-only native successor and fixture sessions are NOT registered Save/signing commands. The presence of `#[cfg(test)]` checks, green CI, or a warning on a form cannot authenticate a user or restrict the underlying legacy handlers.

## 2. Exact primary legacy command matrix

| Tauri command (registered today) | Frontend invocation | Native entry and real existing constraints | Residual risk / proposed interim handling (NOT selected) |
| --- | --- | --- | --- |
| `create_workpaper_revision` | `submitWorkpaperRevision` supplies **three entered fields** plus explicit empty `population`, `sample`, `exceptions`, `managementExplanation`, and `initialOnly: true` | Handler validates workpaper ID; `initialOnly` true calls `create_initial_workpaper_revision` with an atomic first-revision check under SQLite `IMMEDIATE`. **Omitted/false defaults to legacy successor** `create_workpaper_revision`. Persistence appends immutable, seven-field hashed row, supersedes predecessor sign-offs, logs audit; does **not** accept expected latest revision ID or copy predecessor evidence links. | Existing UI blocks its own three-field successor and warns; **other native callers can still omit `initialOnly`**. | `create_workpaper_evidence_link` | `submitWorkpaperEvidenceLink` takes selected document/exact version and relationship | Handler validates ID *shapes* and forwards. Persistence checks exactly one content/controlled version, matching document/version owner, latest revision and no active sign-off before appending a version-resolved link and audit inside `IMMEDIATE`. | No independent per-person workpaper grant in this handler; not the checked, authorized evidence carry-forward path for a new corrected revision. Avoid any blanket assertion that its existing version validation proves custody. |
| `create_workpaper_signoff` | `submitWorkpaperSignoff` sends editable `signoffType`, `actorId`, `actorRole`, optional comment | Handler validates workpaper/revision ID shapes and forwards caller-supplied sign-off fields. Persistence checks workpaper/revision scope and latest revision, requires controlled hash-verified linked evidence and cleared review notes for reviewer/final types, snapshots exact linked IDs and writes sign-off/audit atomically. | **No verified native human principal / signer authorization** in this path. UI warning identifies PREPARED/REVIEWED/FINAL_APPROVAL as unverified legacy labels. Do not represent any such row as independently authenticated approval or transfer it to a successor. |

**Scope distinction:** `list_workpaper_revisions`, `list_workpaper_evidence_links` and `list_workpaper_signoffs` are also registered and currently used to read historical state. Do **not** accidentally break historical read/export while considering a write gate. Other registered, adjacent **mutating** commands—`create_workpaper`, `transition_workpaper_state`, `create_review_note`, `respond_to_review_note`, `clear_review_note`, `reopen_review_note`—and related list commands must be considered in a broader authorization and compatibility review; this packet is a **deep inventory of the three primary revision/evidence/sign-off writes, not a certification of all workpaper mutation surfaces**. In particular, workflow transitions accept a caller-supplied optional `actor_id`; review-note action DTOs have optional caller-provided `actor_id`. No conclusion about their independent trust or severity is made here without separate tracing.

## 3. What is contained today versus still callable

**Already present in this draft/source baseline:** legacy three-field UI displays an explicit draft/unverified warning; its submit refuses creating a successor when it has observed an existing revision, does a fresh list, and sends `initialOnly: true`; the actual native `IMMEDIATE` transaction rejects a second initial revision when that flag is true. The sign-off UI discloses caller-entered actor details. Detached revision UI and the `#[cfg(test)]` successor are isolated. Real SQLite migration tests characterize stale full-snapshot append, sign-off spoofed identity labels, no-op revision append/supersession, immutable history and missing evidence carry-forward. **These are partial containment and characterization, not native-grant access control.**

**Still callable:** `create_workpaper_revision` with missing/false `initialOnly`; `create_workpaper_evidence_link`; `create_workpaper_signoff`; and adjacent registered workpaper-state/review commands. A frontend warning, disabled button or detached editor does NOT remove any of those IPC/native entry points. There is no shipping `expectedLatestRevisionId` CAS editor route, independently bound signer, reviewed `READ_WORKPAPER` / `REVISE_WORKPAPER` grants, or authenticated approval path.

## 4. Concrete containment options for accountable owners — NONE SELECTED

These implement, but do not replace, the L1–L4 decision packet. Each option needs a named product/security human approver, explicit supported platforms, installation compatibility evidence and rollback.

| Option | Proposed native/UX disposition | Safeguards before attempting rollout | Tradeoff |
| --- | --- | --- | --- |
| L1 — visibly **unverified local draft** | Keep legacy command semantics, require unmistakable provenance notices and prevent presenting caller-asserted labels as professional approval | Confirm draft-only risk acceptance; visibility at read/export/print/report consumers, not just entry forms; retained read/history and existing-data census | Preserves operations but still permits caller-asserted sign-offs and stale/native successor appends |
| L2 — reviewed **feature gate** | Gate specifically approved legacy mutating native handlers at the **native** boundary; define defaults for old installations, offline operation and rollback | Preserve independent history reads; backup and export; negative direct-IPC tests (UI bypass); migration/rollback rehearsal; no implicit permission by a UI toggle | Can break existing workflows and is not itself verified person identity |
| L3 — reviewed **disable writes** | Deny selected revision/evidence/sign-off writes at the native entry while retaining trustworthy historical read access | Product/security authorization, versioned migration notice, backup/restore, support path and direct invocation tests | Highest compatibility impact; cannot silently enact |
| L4 — separately authorized **replacement** | New verified person/session + revocable scope-grant native Save and independent reviewer sign-off, with exact-base CAS and evidence custody | DEC-01–08, signed independent review, negative security tests, cross-workpaper authorization, crash/rollback, retention, explicit data provenance | Long-term required route, not implemented/approved |

**Do not quietly switch to L2/L3**, seed administrators/grants, infer consent from green CI, or promote fixture-only `Ok(())` authority. Without an independent security reviewer currently available, record evidence and keep release blocked; there is no substitute signoff or automatic escalation.

## 5. Reversible rollout / historical-data preservation plan (PROPOSAL ONLY)

**Phase 0 — nonmutating reconnaissance:** identify supported build versions and OS/filesystem scope; produce a reviewed inventory of installed caller versions, local/offline usage, integrations and any consumers of sign-off/provenance exports. On **approved copies** of databases only, capture a transactionally consistent backup, schema/migration version, a privacy-minimizing count of workpapers, revision chains, sign-offs by claimed type, active/superseded state, exact evidence links, controlled versions and relevant audit events. Do not extract actor identities or confidential content into a GitHub issue. Record encryption/storage/retention expectations under DEC-05/07.

**Phase 1 — compatibility rehearsal, no shipped change:** for each L1/L2/L3 candidate, rehearse on isolated fixture/copied data: (a) opening and exporting old seven-field revisions with nonempty Unicode/whitespace in the four fields omitted by the old UI, (b) reading superseded sign-offs and exact version IDs, (c) reproducing old calls omitting `initialOnly`, (d) attempted write via direct native IPC rather than React button, (e) current-version UI on an existing workpaper, (f) offline startup and unavailable issuer, (g) protected backup/restore + rollback of application **without rolling back or rewriting legitimate immutable user records**. Stop if unsupported cross-version schema downgrade would destroy rows.

**Phase 2 — owner decision gate:** named product and security humans select L1/L2/L3 or independently reviewed L4, state which exact commands are affected and what to do with old caller-asserted approval labels. Record before/after usability, read-only availability, deployment channels, default flags, reversal, on-disk compatibility, source code owner and accountable sign-off. Resolve DEC-02/03/04/05/06/07/08 as applicable; unresolved items do not default to accept.

**Phase 3 — separately approved implementation/release:** only after the gate, implement native-level denial or verified authorization in a different reviewed change, with direct Tauri command tests, no bypass from old payload shapes, archived-workpaper checks, denial no-mutation, expected-base/evidence-only race checks, exact version/Unicode losslessness, restore, and negative signer identity/grant/revocation. Stage rollout; monitor errors without disclosing confidential workpaper contents. Retain old immutable records and never retroactively label them verified.

**Rollback rule:** rollback of code/gate must not rewrite historical signed rows, recreate forged sign-offs, silently re-enable an unsafe API, or depend on destructive SQLite downgrades. If backward compatibility is impossible, remain read-only with an explicit human-reviewed migration and restore path.
