## Current registered Tauri boundary (non-authorizing)

The following installed/native routes remain registered: `create_statutory_compliance_requirement`, `create_statutory_compliance_assessment`, `list_statutory_compliance_requirements`, `list_statutory_compliance_assessments`, and `list_statutory_compliance_evidence`. Commands validate UUID **shape** and accept caller-selected identifiers and assessment content. They do **not** require a verified native actor, issuer session, engagement-scoped writer/reader grant or independent professional reviewer.

The requirement creator selects an exact immutable firm-library version, rejects non-statutory categories, wrong service scope, archived item and duplicate item per engagement; under `IMMEDIATE` it atomically creates immutable requirement/initial `UNDETERMINED/UNASSESSED` assessment/audit. It checks stored definition hash **length = 32** only. The previous published real-migration tests characterize a synthetic newly inserted mismatched stored digest; this is **not** an installed Tauri database-corruption vector.

`create_statutory_compliance_assessment` first validates allowed status/applicability/date/description combinations and disallows duplicate evidence-version IDs; then obtains `IMMEDIATE`, looks up the exact requirement's `engagement_id`, finds latest assessment, allocates `latest+1`, selects each supplied `controlled_evidence_version_id` with its captured `document_id`, `source_content_version_id`, 32-byte SHA256 and `RETAINED/HASH_VERIFIED` flags, inserts an immutable new assessment and evidence-link snapshot, inserts a `STATUTORY_COMPLIANCE_ASSESSMENT_RECORDED` audit event and commits all under the same transaction. Missing evidence and invalid state prevent writes. The audit helper's `actor_id` is explicitly NULL. A `COMPLIANT` claim requires `APPLICABLE`, actual compliance date, conclusion and at least one qualifying controlled-evidence version, but this validates **data shape/flags, not issuer identity, custody assurance or professional approval**.

### Additional source-verified trust gaps

1. **Caller attribution:** `create_statutory_compliance_assessment` accepts text, dates, applicability, status and evidence IDs from the invoking webview. No verified native user, appointment to this engagement or qualified reviewer signature is represented in the handler or `audit_events.actor_id`.
2. **Archived context:** The assessment persistence function looks up `statutory_compliance_requirements` by ID, but does NOT join the parent `engagements` table or require `archived_at_ms IS NULL` before writing. With a pre-existing requirement, a new assessment can still be appended after the engagement is archived; a test-only migrated database characterizes this **current legacy behavior**, not an endorsed policy or authenticated access bypass.
3. **Evidence provenance:** Each evidence reference must exist and be marked `RETAINED/HASH_VERIFIED`, with 32-byte `sha256`. The assessment routine does NOT recompute hash over controlled bytes, check source scope/client/engagement membership or independently verify that the principal can read/attach the evidence. The storage/capture pipeline's own controls require separate DEC-01/05/07 custody review; existence of metadata flags is not independent attestation.
4. **Concurrency and stale base:** `IMMEDIATE` serializes writes and advances the assessment version. The handler accepts no `expected_latest_assessment_id` CAS and no decision about whether stale whole-form submissions must be refused rather than appended. Historic rows and `source_sha256` link tuples remain immutable, but lineage continuity cannot substitute for authenticated review.
5. **Read scope:** The read commands accept supplied requirement or assessment UUIDs without a verified reader grant. Do not assume knowledge of a UUID provides authorization, nor claim remote reachability before DEC-02 threat-model determination.

## Controlled-evidence read/archive versus assessment attach — 2026-10-21 additional characterization

**Source-inspected differences, not a new permission decision:** `persistence::get_controlled_evidence_read_record` joins `documents` with `d.archived_at_ms IS NULL`. Its caller `evidence::read_controlled_evidence_bytes` also checks `RETAINED/HASH_VERIFIED`, exact controlled locator, managed-root containment, file existence/size and **recalculates SHA-256 over controlled bytes** before returning them. This is a substantive read-path integrity protection and should not be confused with statutory attachment.

In contrast, `persistence::create_statutory_compliance_assessment` reads `controlled_evidence_versions` directly using caller-selected IDs without joining the source `documents` row, checking `documents.archived_at_ms`, enforcing a relationship to the selected engagement/client or invoking `read_controlled_evidence_bytes`. It checks metadata flags and a stored hash **length** and stores exact version/doc/content-version/hash tuples in immutable `statutory_compliance_evidence_links`. A successful metadata attachment **does not certify controlled bytes were reread, grant permission to reuse evidence, or establish professional approval**.

[Three new nonshipping real-migration tests](../../src-tauri/src/workpaper_statutory_assessment_native_tests.rs) create a **synthetic full FK-valid SQLite source and capture lineage** only inside disposable fixtures, deliberately without writing real controlled evidence bytes. These tests:
- Characterize a `COMPLIANT` assessment attaching stored `RETAINED/HASH_VERIFIED` **synthetic metadata**, preserving the exact source document/content version/hash tuple and immutability trigger; audit `actor_id` is still NULL.
- Archive the fixture source `documents` row; the normal `get_controlled_evidence_read_record` returns `None` while the current statutory metadata attachment still appends an immutable assessment/evidence-link record. This is a **read/attach archive-consistency gap** under synthetic metadata and does not demonstrate a normal installed Tauri user can invent a capture or bypass controlled-byte verification.
- Assert `QUARANTINED` controlled metadata cannot support a `COMPLIANT` assessment and failed attachment produces **zero assessment, evidence-link or audit writes**.

[Source-only Node tripwires](../../tests/workpaper-firm-library-boundary.test.mjs) track the read/attach distinction and 9/34 unchanged denial ledger. They are neither direct native IPC denials nor positive evidence-custody assertions.

**Human acceptance, NOT IMPLEMENTED / NOT RUN:** DEC-01/02/04/05/06/07/08 must determine document archival consequences (deny new links versus retain historical read-only links), verified cross-engagement evidence sharing and reader/writer grants, whether authoritative attachment must independently revalidate bytes under a user-scoped trust boundary, expected version CAS/revocation, audit identity and lawful retention. ## Genuine controlled bytes after capture: lost-byte and digest-mismatch attachment (2026-10-21, nonshipping)

Two additional cases in [`evidence.rs`](../../src-tauri/src/evidence.rs) use the **actual native file indexer, byte-copy/rehash-verified controlled capture and production SQLite migrations**, rather than the synthetic `controlled_evidence_versions` INSERT fixtures described earlier. Each creates a genuine firm-library statutory requirement/engagement via persistence, then deliberately damages **only an isolated, disposable controlled file** after successful verified capture. In both cases the normal `read_controlled_evidence_bytes` refuses access **while the existing `create_statutory_compliance_assessment` persistence writer still appends caller-claimed `COMPLIANT` based only on retained/hash-verified database flags**:

- **Same-length controlled-byte modification:** capture and baseline real-byte read succeed. A one-byte mutation, made writable only within the fixture, preserves file length but invalidates SHA-256. The normal read rejects it as `Integrity`. The metadata-only statutory writer does not reopen controlled bytes and still snapshots the original controlled version, source document/content ID and stored original digest in an immutable assessment evidence link.
- **Managed controlled file missing:** capture and baseline byte read succeed, then the disposable controlled file is removed. The read path rejects the missing file as `Configuration`. The statutory writer still attaches the stale metadata tuple and records a `COMPLIANT` assessment.

**Why this differs from prior synthetic metadata-only tests:** both cases begin with *genuinely verified, actually captured bytes* and demonstrate a post-capture **read-failure-versus-new-assessment-attachment inconsistency** under nonshipping local file fault injection. They do **not** demonstrate malicious access to another user's machine, untrusted direct Tauri command grants, forged native capture, qualified professional signoff or the reason bytes might become corrupted/missing in deployment. The fixtures invoke native `evidence::capture_controlled_evidence` and lower-level `persistence::create_statutory_compliance_assessment` **directly**, not a registered authenticated Tauri session. No evidence held outside the temp fixture is ever modified.
