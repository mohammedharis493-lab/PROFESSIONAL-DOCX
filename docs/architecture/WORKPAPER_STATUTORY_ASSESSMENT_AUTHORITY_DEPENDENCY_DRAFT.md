## Current registered Tauri boundary (non-authorizing)

The following installed/native routes remain registered: `create_statutory_compliance_requirement`, `create_statutory_compliance_assessment`, `list_statutory_compliance_requirements`, `list_statutory_compliance_assessments`, and `list_statutory_compliance_evidence`. Commands validate UUID **shape** and accept caller-selected identifiers and assessment content. They do **not** require a verified native actor, issuer session, engagement-scoped writer/reader grant or independent professional reviewer.

The requirement creator selects an exact immutable firm-library version, rejects non-statutory categories, wrong service scope, archived item and duplicate item per engagement; under `IMMEDIATE` it atomically creates immutable requirement/initial `UNDETERMINED/UNASSESSED` assessment/audit. It checks stored definition hash **length = 32** only. The previous published real-migration tests characterize a synthetic newly inserted mismatched stored digest; this is **not** an installed Tauri database-corruption vector.

`create_statutory_compliance_assessment` first validates allowed status/applicability/date/description combinations and disallows duplicate evidence-version IDs; then obtains `IMMEDIATE`, looks up the exact requirement's `engagement_id`, finds latest assessment, allocates `latest+1`, selects each supplied `controlled_evidence_version_id` with its captured `document_id`, `source_content_version_id`, 32-byte SHA256 and `RETAINED/HASH_VERIFIED` flags, inserts an immutable new assessment and evidence-link snapshot, inserts a `STATUTORY_COMPLIANCE_ASSESSMENT_RECORDED` audit event and commits all under the same transaction. Missing evidence and invalid state prevent writes. The audit helper's `actor_id` is explicitly NULL. A `COMPLIANT` claim requires `APPLICABLE`, actual compliance date, conclusion and at least one qualifying controlled-evidence version, but this validates **data shape/flags, not issuer identity, custody assurance or professional approval**.

### Additional source-verified trust gaps

1. **Caller attribution:** `create_statutory_compliance_assessment` accepts text, dates, applicability, status and evidence IDs from the invoking webview. No verified native user, appointment to this engagement or qualified reviewer signature is represented in the handler or `audit_events.actor_id`.
2. **Archived context:** The assessment persistence function looks up `statutory_compliance_requirements` by ID, but does NOT join the parent `engagements` table or require `archived_at_ms IS NULL` before writing. With a pre-existing requirement, a new assessment can still be appended after the engagement is archived; a test-only migrated database characterizes this **current legacy behavior**, not an endorsed policy or authenticated access bypass.
3. **Evidence provenance:** Each evidence reference must exist and be marked `RETAINED/HASH_VERIFIED`, with 32-byte `sha256`. The assessment routine does NOT recompute hash over controlled bytes, check source scope/client/engagement membership or independently verify that the principal can read/attach the evidence. The storage/capture pipeline's own controls require separate DEC-01/05/07 custody review; existence of metadata flags is not independent attestation.
4. **Concurrency and stale base:** `IMMEDIATE` serializes writes and advances the assessment version. The handler accepts no `expected_latest_assessment_id` CAS and no decision about whether stale whole-form submissions must be refused rather than appended. Historic rows and `source_sha256` link tuples remain immutable, but lineage continuity cannot substitute for authenticated review.
5. **Read scope:** The read commands accept supplied requirement or assessment UUIDs without a verified reader grant. Do not assume knowledge of a UUID provides authorization, nor claim remote reachability before DEC-02 threat-model determination.
